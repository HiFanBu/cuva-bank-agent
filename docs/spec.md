# CuVA 复刻版 — 技术 Spec

Nov 6, 2026 · @Martin

用公开资料和模拟数据重建一个 CuVA 风格的信用卡 AI 助手。不使用 Barclays 的代码、数据或内部细节。

## 1. 目标

让已登录的信用卡客户通过 chat 自助解决常见问题，减少转人工，同时保证回答准确、操作安全、投诉合规。

| 项 | 内容 |
| --- | --- |
| **问题** | 人工客服成本高，大量重复问题可以自助处理 |
| **用户** | 已登录的模拟信用卡客户 |
| **主指标** | 评测集上的自助解决率 |
| **护栏** | 错误操作为 0，越权调用为 0，不漏投诉或争议 |
| **面试目标** | 能用代码讲清 Agent loop、工具、RAG、评测、护栏、路由和监控 |

## 2. 范围

v1 按 Knowledge、Payment、Complaint 的顺序交付，先用简单路由，等实验证明价值后再加 supervisor。

| 模块 | 做 | 不做 |
| --- | --- | --- |
| **Knowledge** | 基于公开信用卡条款回答政策问题，带引用 | 编造或解释没有来源的政策 |
| **Payment** | 查余额、账单、交易；确认后安排还款 | 真实转账、退款、减免费用 |
| **Complaint** | 识别投诉和争议，生成摘要并转人工 | 判定投诉结果或争议责任 |
| **平台** | 评测、护栏、追踪、缓存、模型路由、Docker | 前端、语音、Kubernetes、模型微调 |

**必须转人工：** 用户要求、欺诈或未授权交易、账单争议、需要决定的投诉、置信度低、连续失败、脆弱客户迹象。

## 3. 行为

每条请求都走同一个流程：输入护栏、路由、Agent loop、工具或 RAG、输出检查，最后回答、请求确认或转人工。

**正常流程**

| 场景 | 用户输入 | 系统行为 | 结果 |
| --- | --- | --- | --- |
| 政策问答 | “逾期费怎么收？” | 混合检索条款，生成带引用的回答 | `answered` + citations |
| 查余额 | “我的余额是多少？” | 调用 `get_balance` | `answered` |
| 安排还款 | “11 月 12 日还 500 美元” | 校验参数，生成待确认动作 | `needs_confirmation` |
| 确认还款 | 点击确认 | 校验本人和过期时间后执行，写审计日志 | `answered` |
| 投诉 | “我被重复扣款了” | 分类为争议，生成摘要 | `handoff` |

**异常流程**

| 异常 | 处理 |
| --- | --- |
| 模型输出不合 schema | 反馈错误并重试，最多 2 次，之后 `failed` 并转人工 |
| 未知工具或参数非法 | 不执行，把错误作为观察结果返回给模型 |
| 工具超时或异常 | 有限次数重试，失败后转人工 |
| 模型 API 超时 | 重试一次或切备用模型，仍失败则返回友好提示 |
| 检索证据不足 | 拒答，并提供转人工选项 |
| 超过 6 步 | 停止循环并转人工 |
| 确认者不是本人或动作过期 | 拒绝执行 |

**边界条件**

- 金额必须大于 0，且不超过设定上限。
- 还款日期不能早于今天。
- 同一笔还款重复提交只执行一次。
- 文档或用户输入里的指令不能改变工具权限。
- 账户类问题不进入语义缓存。
- 一条消息同时包含多个意图时，优先处理风险更高的投诉或争议。

## 4. 接口

用户身份由服务端从认证信息中获取，不在请求体里传，也不由模型决定。

**API**

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `POST` | `/chat` | 发送消息 |
| `POST` | `/chat/confirm` | 确认待执行动作 |
| `GET` | `/health` | 健康检查 |
| `GET` | `/metrics` | 延迟、成本、错误率 |

**请求和响应**

```json
// POST /chat
{"conversation_id": "c_123", "message": "How is the late fee charged?"}

// response
{"status": "answered | needs_confirmation | handoff | failed",
 "message": "...", "citations": [{"doc_id": "tos", "section": "Late fees"}],
 "action_id": null, "trace_id": "t_456"}
```

**模型输出（AgentStep）**

```json
{"type": "tool_call", "tool": "schedule_payment", "args": {"amount_cents": 50000, "pay_date": "2026-11-12"}}
{"type": "final", "message": "...", "citations": []}
{"type": "handoff", "reason": "billing_dispute", "summary": "..."}
```

**工具**

| 工具 | 参数 | 风险 | 需要确认 |
| --- | --- | --- | --- |
| `search_policy` | `query` | 低 | 否 |
| `get_balance` | 无 | 中 | 否 |
| `get_transactions` | `limit` | 中 | 否 |
| `schedule_payment` | `amount_cents`、`pay_date` | 高 | 是 |
| `create_case` | `category`、`summary` | 高 | 否，必须转人工 |

**数据表**

| 表 | 关键字段 |
| --- | --- |
| `accounts` | `user_id`、`balance_cents`、`due_date` |
| `transactions` | `id`、`user_id`、`amount_cents`、`merchant`、`posted_at` |
| `payments` | `id`、`user_id`、`amount_cents`、`pay_date`、`idempotency_key` |
| `pending_actions` | `action_id`、`user_id`、`tool`、`args`、`expires_at` |
| `cases` | `id`、`user_id`、`category`、`summary`、`status` |
| `audit_log` | `trace_id`、`user_id`、`event`、`tool`、`created_at` |
| `documents` | `doc_id`、`chunk_id`、`text`、`embedding` |

## 5. 约束

安全规则写在代码里，不依赖 prompt。

| 类别 | 约束 |
| --- | --- |
| **安全** | 服务端做身份、权限和参数校验；每个工具最小权限；日志和模型输入脱敏 PII；检索文档和用户输入都当数据，不当指令 |
| **可靠性** | 幂等执行；待确认动作 10 分钟过期；工具和模型调用设超时；最多 6 步 |
| **性能** | 起始目标 p95 < 5 秒；记录每次对话的 token 和成本 |
| **技术栈** | Python、FastAPI、Pydantic、SQLite、pytest、Docker Compose |
| **模型** | 通过 `llm.py` 接入，可替换供应商；测试用固定的假模型 |
| **禁止** | 使用 Barclays 代码或数据；用 Agent 框架替代手写 loop；模型决定 `user_id`；未确认就动钱；提交 API key |

## 6. 验收标准

所有测试在 CI 里通过才算完成；评测指标低于门槛时阻止合并。

**功能测试**

- [ ] 政策问题返回答案和至少一个引用
- [ ] 无证据时拒答，不编造政策
- [ ] 余额和交易只返回当前用户的数据
- [ ] 还款必须确认；非本人或过期确认被拒绝
- [ ] 重复提交同一笔还款只生成一条记录
- [ ] 投诉和争议进入 `handoff` 并生成摘要

**稳定性和安全测试**

- [ ] 非法 JSON 修复成功；连续失败安全退出
- [ ] Agent loop 不超过 6 步
- [ ] 模型传入他人 `user_id` 时被拒绝
- [ ] Prompt injection 测试不能触发未授权工具
- [ ] 日志里没有未脱敏的 PII

**评测门槛（起始目标）**

| 指标 | 门槛 |
| --- | --- |
| 任务完成率 | ≥ 80% |
| 回答质量 | ≥ 4 分（满分 5 分） |
| 错误操作和越权调用 | 0 |
| 投诉和争议漏报 | 0 |
| Prompt injection 拦截率 | ≥ 95% |
| p95 延迟 | < 5 秒 |

## 7. Guardrail 与合规

Guardrail 是分层控制加合规流程：Compliance 定义什么不能发生，产品和工程设计系统如何保证，并用测试证明。

**分层控制**

| 层级 | 防什么 | 控制 |
| --- | --- | --- |
| 输入 | 注入、越权、敏感信息 | 意图识别、注入检测、PII 脱敏、高风险意图转人工 |
| 检索 | 用错文档、文档内恶意指令 | 只用批准文档，按权限过滤，文档当数据 |
| 工具 | 越权和错误扣款 | 服务端校验、最小权限、限额、确认、幂等 |
| 输出 | 编造政策、违规承诺、泄露信息 | 引用检查、禁用表述检查、敏感信息检查、无证据拒答 |
| 人工兜底 | 自动化不该处理的情况 | 投诉、争议、欺诈、低置信度转人工；保留审计日志 |

**和 Compliance 的合作流程**

| 步骤 | 产品和工程 | Compliance |
| --- | --- | --- |
| 1. 识别风险 | 整理场景和 AI 能力边界 | 指出相关法规和内部政策 |
| 2. 定义红线 | 转成可执行的系统规则 | 确认规则完整、表述合规 |
| 3. 控制映射 | 每个风险对应护栏、日志和转人工 | 审核控制是否充分 |
| 4. 测试集 | 建用例和评测指标 | 提供难例并抽检 |
| 5. 上线审批 | 提交评测报告 | 签字确认上线条件 |
| 6. 监控复盘 | 追踪违规、误拦和事故 | 定期抽检，规则变化时更新 |

**指标：** 同时看漏拦率和误拦率。投诉、争议和资金操作的漏拦要接近 0，可以接受较高的误拦；再用转人工率判断护栏是否过严。

本节是产品和工程设计，实际规则以法务和合规审核为准。

## 8. Payment 高并发设计

Payment 量大时，核心原则是把 LLM 从资金路径上拿开：模型只理解意图和抽取参数，确认后的执行由确定性的支付服务完成。

&#91;embedded content: Payment 高并发流程\]

**关键设计**

| 问题 | 方案 |
| --- | --- |
| LLM 是最慢、最贵的环节 | 意图明确时用规则或小模型直接进表单式流程，不走大模型；复杂或模糊情况才用 LLM |
| 服务要水平扩展 | Chat API 无状态，对话和待确认动作存 Redis 并设 TTL |
| 重试不能重复扣款 | 每笔支付带 idempotency key，数据库唯一约束 |
| 支付不能丢 | Outbox 模式：支付记录和消息同一事务写入，再由队列异步执行 |
| 下游故障 | 重试加退避、死信队列、失败后的补偿和通知 |
| 流量高峰 | 用户和全局限流；LLM 超载时熔断，切到表单式还款或人工 |
| 读请求量大 | 余额和账单走只读副本，可加短 TTL 缓存，并在回答中标明数据时间 |
| 可追溯 | 每个请求带 trace ID，记录延迟、成本、工具结果和审计日志 |

**容量估算公式**

```latex
QPS_{peak} = \frac{\text{daily payment conversations} \times \text{peak factor}}{86400}
```

```latex
LLM\ capacity = QPS_{peak} \times \text{LLM share} \times \text{calls per conversation}
```

用实际或假设的对话量、高峰倍数和 LLM 占比代入，得到需要的模型配额、worker 数和数据库写入量。

**验收**

- [ ] 压测时支付不重复、不丢失
- [ ] LLM 不可用时，用户仍能通过表单式流程或人工完成还款
- [ ] Worker 崩溃后重启，队列里的支付只执行一次
- [ ] 高峰时触发限流和熔断，而不是拖垮核心服务

## 9. 已确定的技术决策

架构是 Spring Boot + Python + MCP，分三个阶段交付，每个阶段都能独立演示。

| 决策 | 选择 |
| --- | --- |
| **生产模型** | AWS Bedrock（Converse API） |
| **本地开发模型** | Ollama 本地开源模型，免费、部署最快 |
| **知识库** | Capital One 公开信用卡协议 |
| **评测问题** | CFPB 公开投诉数据里的信用卡问题 |

**服务分工**

| 服务 | 负责 |
| --- | --- |
| **Spring Boot** | 对外 REST API、身份认证、账户和交易数据、待确认动作、支付执行、审计日志；作为 MCP Server 暴露账户工具 |
| **Python AI 服务** | Agent loop、RAG、评测、护栏、路由、模型调用；作为 MCP Client 调用工具 |

**交付阶段**

| 阶段 | 内容 | 可演示结果 |
| --- | --- | --- |
| 1. Python 核心 | 模型接入、Agent loop、RAG、评测、护栏 | 单服务跑通政策问答和还款 |
| 2. MCP | 把工具改为 MCP Server，Agent 改为 MCP Client | 工具可独立发现和调用 |
| 3. Spring Boot | Java 实现账户服务和 MCP Server，接管权限、确认和审计 | 银行式的完整架构 |

先把 Python 核心做稳，再拆服务。如果面试前做不完阶段 3，就把它作为下一步的设计来讲。
